# Scripture Card 51장 자연어 추천 평가 계획 (2026-09-15)

이 문서는 Scripture Card 51장(Scripture Card Expansion v2, `docs/SCRIPTURE_CARD_EXPANSION_2026-09-15.md`)이
실제 자연어 입력에서도 제대로 추천되는지 평가하기 위해 준비한 자료와 절차, 실제 실행 결과를 적는다.

## 1. 51장은 "평가를 시작할 수 있는 카드 기준선"이다

51장은 완성된 최종 카드 수가 아니라, 지금부터 자연어 평가를 시작할 수 있는 출발점이다.
`scripts/scripture-recommendation-evaluation-cases.ts`의 `preferredCardId`/`acceptableCardIds`는
사람이 각 문장과 카드의 situationTags를 직접 대조해서 세운 **평가 가설**이지, 코드가 의미상
겹침을 자동으로 "검증"한 결과가 아니다. `src/lib/scripture-recommendation-evaluation-cases.test.ts`가
실제로 확인하는 것은 원본 위치(문장·domain·rank·cluster가 EXPANSION_SCENARIOS와 일치)·개수
(총 153개)·카드 영역 소속·문장과 ID 중복 없음·안전 경계 사례(`SAFETY_BOUNDARY_SCENARIOS`)
와의 교집합이 0건이라는 **데이터 정합성**뿐이다. 이 정적 검증을 통과했다고 자연어 추천이 실제로
잘 된다는 뜻은 아니다 — 그것은 아래 §4의 실제 호출로만 확인한다.

## 2. 태그 분리 테스트는 자연어 Analyzer 정확도를 증명하지 않는다

`scripture-expansion-simulation.test.ts`의 situationTags 분리 무결성 테스트와, 이번에 추가한
`scripture-recommendation-evaluation-cases.test.ts`는 둘 다 **정적 데이터** 테스트다.

- 확인하는 것: 카드에 저장된 태그를 그대로 Gate에 되먹였을 때 같은 영역의 다른 카드와
  분리되어 단독 1위가 되는가. 평가 자료의 구조와 카드·영역 관계가 유효한가.
- 확인하지 않는 것: 실제 사용자가 쓴 자연어 문장에서 Situation Analyzer(OpenAI)가 그 태그를
  정확히 뽑아내는가. 이것은 OpenAI를 실제로 불러야만 알 수 있고, `npm run test:logic`이나
  `npm test`로는 절대 증명되지 않는다.

이 구분을 분명히 하는 이유는, 태그 테스트가 전부 통과한 것을 "51장이 실제 대화에서도 잘 작동한다"는
증거로 착각하지 않기 위해서다.

## 3. 평가 자료

- `scripts/situation-scenario-corpus.ts`의 `EXPANSION_SCENARIOS`(17개 영역 × 20문장 = 340문장,
  기존 자료, 이번에 수정하지 않음)에서만 문장을 가져왔다.
- `scripts/scripture-recommendation-evaluation-cases.ts` — 새로 만든 153개 평가 코퍼스.
  문장을 새로 짓지 않았고,
  `SAFETY_BOUNDARY_SCENARIOS`(안전 경계로 확정된 문장)와는 domain·rank·text 세 값을 모두
  대조해 교집합이 0건임을 정적 테스트로 직접 확인한다(도메인이 EXPANSION_SCENARIOS에 속한다는
  것만으로는 안전 경계 제외를 증명하지 않는다 — 안전 경계 문장도 같은 도메인에 속하기 때문이다).
  각 사례는 원본 코퍼스의 domain·rank·cluster를 그대로 달고 있어 `EXPANSION_SCENARIOS`와
  항상 대조할 수 있다.
- 자연어 153건은 현재 `recommend` 148건, `domain_choice` 2건, `no_coverage` 3건으로 나뉜다.
  실제 앱이 지원하는 정상 경로를 모두 평가하며, 모든 문장을 억지로 카드 추천으로 만들지 않는다.
- `recommend` 기대 사례만 `preferredCardId`(1위로 기대하는 카드)와 `acceptableCardIds`(1~2장, preferred 포함 — top1이
  이 중 하나면 합리적이라고 인정)를 구분했다. "신규 카드는 예전 일반 카드를 자동으로 acceptable에
  넣는다"거나 "카드가 3장씩 함께 생긴 영역은 대안을 넣지 않는다" 같은 일괄 규칙 없이, 같은
  영역 카드 3장의 situationTags와 문장 내용을 매 사례마다 직접 대조해서 정했다. acceptable은
  둘 다 실제로 목회적으로 자연스러운 경우에만 넣었고, 그 이유는 각 사례의 `rationale`과 파일
  상단 주석에 적었다 — 같은 영역 카드 3장을 전부 허용해 평가를 약화하지 않았다.
- 최초에는 카드 51장을 각각 3번씩 preferred로 배정했지만, 2026-09-16 실제 new-cards 실행에서
  자연스러운 인생 방향 문장을 SC-051에 억지로 배정한 오류가 확인됐다. 이 균형 조건은 폐기했다.
  원본 코퍼스의 `domain`은 출처 위치를 보존하는 편집 정보이고, 실제 문장 의미에 따른
  `expectedPrimaryDomain`과 다를 수 있다.
- `NEW_CARD_REACHABILITY_CASES`는 SC-032~SC-051 각각의 좁은 상황 전제를 직접 표현하는 별도
  20문장이다. 새 카드가 Analyzer→Gate의 실제 경로에서 도달 가능한지를 확인하되, 자연어 153건의
  정답 분포를 카드 수에 맞춰 왜곡하지 않는다.

## 4. 실행 순서 — smoke → new-cards → full

실제 OpenAI 호출은 한 번에 153건을 다 부르지 않고, 아래 순서로 단계별로 확인한다.

1. **smoke** (`--mode=smoke`, 17건) — 17개 영역에서 대표 카드 한 장씩만 부른다. 구조 검증·안전
   오탐·domain 일치 같은 기본 배선이 살아있는지 가장 적은 호출로 먼저 확인한다.
2. **new-cards** (`--mode=new-cards`, 20건) — 별도 `NEW_CARD_REACHABILITY_CASES`로 이번에 새로
   추가된 SC-032~SC-051이 각각 최소 한 번은 실제로 1위로 뽑히는지 확인한다. 이 단계는 자연어
   빈도나 일반 품질 점수가 아니라 카드별 도달 가능성을 검사한다.
3. **full** (`--mode=full`, 153건) — 앞의 두 단계에서 큰 문제가 없을 때만 전체를 돌린다.

각 단계는 `node scripts/test-openai-recommendation-e2e.ts --mode=<smoke|new-cards|full>`로 실행한다.
`--dry-run`을 더하면 OpenAI를 부르지 않고 그 모드가 실제로 어떤 사례를 고르는지만 먼저 눈으로
확인할 수 있다. 모드를 지정하지 않고 실행하면 사용법만 출력하고 아무것도 호출하지 않는다.

## 5. 실제 호출은 별도 승인 뒤에만 실행한다

평가 자료·도구를 준비한 뒤 별도 승인을 받아 smoke와 new-cards 실제 호출을 실행했다. 앞으로도
`--mode=smoke` 등 실제 호출은 별도 승인을 받은 뒤에만 한다. `OPENAI_API_KEY`가 없으면
`scripts/analyzer-prompt.ts`의 `createClient()`가 즉시 안내만 하고 종료한다. API Key는 저장소나
평가 로그에 기록하지 않고, 실행이 끝나면 셸 변수에서도 지운다.

## 6. 호출 횟수와 토큰은 보고하되 금액은 문서에 고정하지 않는다

각 단계 실행 결과는 다음을 각각 나눠 보고한다(`scripts/test-openai-recommendation-e2e.ts`의
출력 형식).

1. 응답 구조 검증 성공률
2. 안전 오탐 수 (안전 경계 문장이 아닌데 `route: 'safety'`로 온 경우)
3. domain 기대 일치율 (`domain_choice`는 두 후보 집합까지 확인)
4. `recommend` 기대 사례의 preferred 카드 1위 일치율
5. `recommend` 기대 사례의 acceptable 카드 일치율
6. 기대 route 불일치 수
7. 입력·출력·전체 토큰 사용량(input / output / total)

실제 보고 항목은 위 7개다(토큰 사용량의 input/output/total은 7번 항목 하나의 하위 수치이지
별개 항목이 아니다). 실행 결과는 총계만 보여주지 않고, 구조 검증 실패·안전 오탐·primary
domain 불일치·preferred 불일치·acceptable 불일치·route 불일치별로 실패한 평가 ID를 나눠 출력한다.

토큰 사용량은 실행 시점의 실제 응답 기준으로 그때그때 보고한다. OpenAI 요금은 모델·시점에 따라
바뀌므로, 이 문서에는 "몇 건 호출 시 예상 비용이 얼마"처럼 변동 가능한 금액을 고정해서 적지 않는다.
비용을 가늠해야 하면 실행 시점의 실제 토큰 사용량과 그 시점의 공개 요금표를 따로 대조한다.

API Key, 사용자 문장, 모델 원본 응답은 파일에 자동 저장하지 않는다 — 모든 출력은 콘솔(stdout)뿐이고,
결과를 남기고 싶으면 실행하는 사람이 직접 `tee`를 붙인다.

## 7. 지인 베타 전 단계별 통과 기준

첫 smoke와 기존 new-cards 실행으로 구조·안전은 안정적이지만, 카드별 도달성과 자연어 평가를
분리해야 한다는 사실을 확인했다. 이후 실행은 다음 기준으로 판단한다.

- smoke: 구조 100%, 안전 오탐 0, primary domain 100%, acceptable 100%, 예상 밖 route 0.
- new-cards 도달성: 20장 모두 구조·domain·preferred·acceptable 일치, 안전 오탐과 예상 밖 route 0.
- full 자연어 품질: 구조 100%, 안전 오탐 0을 필수로 하고, primary domain과 acceptable 결과는
  실패 문장을 사람이 다시 검토한다. preferred는 카드 다양성을 관찰하는 지표로 함께 보고하되,
  사람이 허용한 다른 카드가 선택된 사례를 곧바로 제품 실패로 간주하지 않는다.

full의 최종 수치 기준은 이 교정 후 첫 153건 결과와 실패 유형을 보고 확정한다. 숫자 하나로 통과를
선언하기보다, 안전·영역·카드 의미·도달성 네 항목을 분리해 판단한다.

## 8. 실제 실행 기록

### 8-1. 최초 smoke 17건

분석 지시문을 교정하기 전에 실행한 기준선 결과다. 구조 17/17, 안전 오탐 0/17,
primary domain 17/17, preferred 13/17, acceptable 14/17이었고 예상 밖 ambiguous가 2건이었다.
토큰은 input 168,914 / output 2,875 / total 171,789였다. 이 실행 뒤 태그 경계 지시문이
바뀌었으므로 현재 지시문의 최종 smoke 통과 증거로 사용하지 않는다.

### 8-2. 신규 카드 SC-032~SC-051 도달성

최종 분석 지시문으로 20건을 실행했을 때 19건이 일치했고, REACH-040만 첫 문장의 과로 호소 때문에
`burnout_exhaustion`으로 분류됐다. 이는 런타임 분류 오류라기보다 도달성 평가 문장이 두 영역을
함께 표현한 문제로 판단했다. REACH-040의 문장만 `바쁘게 보낸 하루를 잠시 멈추고, 하나님과 따로
조용히 머물며 쉬고 싶어요.`로 좁혔고, 같은 분석 지시문·카드·Gate로 단일 재실행해
`quiet_communion` / SC-040(87.5점) 일치를 확인했다.

따라서 현재 근거는 **동일한 런타임에서 일괄 통과한 19건 + 문장만 교정해 단일 통과한 REACH-040**이며,
SC-032~SC-051은 각각 실제 Analyzer→Gate 경로에서 한 번 이상 의도한 카드로 도달했다. 20건이 한 번의
일괄 실행에서 모두 통과했다고 기록하지 않는다. 19건 일괄 실행의 토큰은 input 217,169 /
output 4,180 / total 221,349였고, REACH-040 단일 재실행은 input 10,861 / output 132 /
total 10,993이었다.

이후 현재 smoke에서 일반 지혜 문장 EVAL-082를 SC-051이 가로채는 문제가 드러나, SC-051에서
넓은 `무엇이 더 나은지 분별함` situationTag를 제거했다. 이 변경 뒤 REACH-051을 다시 실행해
`wisdom_discernment` / SC-051(65점) 일치를 확인했다. 토큰은 input 10,824 / output 229 /
total 11,053이었다. 따라서 SC-051도 최종 카드 태그 상태에서 도달성이 다시 확인됐다.

### 8-3. 직전 smoke 17건

태그 경계 지시문 교정 뒤 다시 실행한 결과는 구조 17/17, 안전 오탐 0/17, primary domain 17/17,
preferred 16/17, acceptable 16/17, 예상 밖 route 0/17이었다. 토큰은 input 184,418 /
output 2,373 / total 186,791이었다.

유일한 실패 EVAL-082는 일반적인 판단 어려움인데 SC-051의 넓은 situationTag 때문에 SC-051이
선택된 사례였다. 해당 태그만 제거한 뒤 EVAL-082를 단일 재실행해 `wisdom_discernment` /
SC-010(90점) 일치를 확인했다. SC-051 자체가 사라지지 않았는지는 같은 변경 상태에서 REACH-051로
함께 확인했다. EVAL-082 단일 재실행의 토큰은 input 10,806 / output 186 / total 10,992였다.

현재 smoke 통과 근거는 **같은 분석 지시문으로 일괄 통과한 16건 + 카드 태그만 교정한 뒤 단일
통과한 EVAL-082**다. 17건이 한 번의 일괄 실행에서 모두 통과했다고 기록하지 않는다.

### 8-4. 최초 full 153건 기준선

평가 계약과 추가 영역 경계를 교정하기 전에 처음 실행한 full 결과는 구조 153/153, 안전 오탐 0,
primary domain 130/153(85.0%), preferred 78/153(51.0%), acceptable 98/153(64.1%), 예상 밖
route 26/153이었다. 토큰은 input 1,653,418 / output 38,713 / total 1,692,131이었다.

이 결과는 출시 통과 결과가 아니다. 실패를 전수 검토한 뒤 27건의 평가 가설을 문장 의미에 맞게
교정했고, 그중 EVAL-094·140은 `domain_choice`, EVAL-111·117·143은 `no_coverage`가 정답임을
명시했다. 나머지 동점과 분석 오류는 계속 실패로 남긴다. 이후 Analyzer 지시문도 자녀 양육,
구직, 치료, 의심에 대한 죄책감, 사과 책임, 분류 근거가 없는 죽음 표현의 경계를 보강했다.
그러므로 위 수치는 현재 코드의 최종 품질 수치로 재사용하지 않고, 교정 전 기준선으로만 보존한다.

### 8-5. 후속 full 실행 스냅샷

평가 가설과 태그 경계를 한 차례 교정한 뒤 실행한 full 결과는 구조 153/153, 안전 오탐 0,
primary domain 149/153(97.4%), preferred 115/148(77.7%), acceptable 129/148(87.2%),
기대 route 불일치 14/153이었다. 토큰은 input 2,090,845 / output 33,773 /
total 2,124,618이었다.

이후 추가 교정 중 다시 실행한 가장 최근 full 결과는 구조 153/153, 안전 오탐 1/153,
primary domain 150/153(98.0%), preferred 118/148(79.7%), acceptable 131/148(88.5%),
기대 route 불일치 14/153이었다. 토큰은 input 2,107,216 / output 28,411 /
total 2,135,627이었다. 이때의 안전 오탐은 EVAL-143 한 건, primary domain 불일치는
EVAL-089·116·129였다.

두 수치는 모두 유용한 진행 기록이지만 **현재 최종 태그와 지시문보다 이전 상태의 스냅샷**이다.
특히 두 번째 실행 뒤 EVAL-089·116·129의 영역 경계, EVAL-143의 안전 경계와 반복 동점 사례를
추가로 고쳤다. 따라서 88.5%를 현재 코드의 정확한 최종 acceptable 비율로 단정하지 않으며,
반대로 후속 표적 검사가 통과했다는 이유만으로 전체 153건이 모두 통과했다고 주장하지 않는다.

### 8-6. 후속 표적 반복 검사

전체 실행에서 반복되거나 의미 경계가 분명했던 실패는 같은 입력을 여러 번 호출해 수정 전후의
안정성을 확인했다.

- EVAL-051·069 영역 경계: 각 3회, **6/6 통과**. EVAL-051은
  `relationship_conflict_forgiveness` / SC-031, EVAL-069는
  `injustice_mistreatment` / SC-008 계열로 안정됐다. total tokens 83,409.
- EVAL-080·089·116·129·143: 각 3회, **15/15 통과**. 상실 카드 경계, 결정·소진 영역,
  치료비가 원인인 복합 상황의 우선 영역, 안전 경계가 의도한 계약으로 반복됐다.
  total tokens 213,120.
- 반복 동점 EVAL-008·086·095·096·114·134: 첫 반복 검사에서 **17/18 통과**했고,
  EVAL-096 한 번만 SC-024로 갈렸다. SC-014의 `교제` 목회 기능과 분석 경계를 보강한 뒤
  EVAL-096을 3회 다시 실행해 **3/3 통과**했다. 마지막 재검사의 total tokens 44,924.
- 신규 카드 20장은 일괄 19건 통과 뒤 실패 문장·태그를 교정하고 해당 사례를 재검사해,
  각 카드가 최종 매칭 상태에서 실제 Analyzer→Gate 경로로 한 번 이상 도달함을 확인했다.
  이는 한 번의 최종 일괄 실행에서 20/20이 나왔다는 뜻은 아니다.

후속 검사는 수정한 경계가 같은 입력에서 반복 재현되는지를 확인한다. 153개 전체 분포의 정확한
최종 비율을 다시 계산한 검사는 아니므로, 전체 통계와 표적 안정성 근거를 서로 바꾸어 쓰지 않는다.

## 9. 지인 베타 전 판단과 다음 단계

2026-09-15에 프로젝트 소유자가 51개 말씀 카드의 본문·설명·기도 방향·추천 기준·오용 방지
문구를 전체 검토했고, 말씀 콘텐츠 검토를 완료로 승인했다. 남은 검토는 최신 서버 함수를 연결한
실제 앱에서 상황 입력→영역 선택→말씀→기도 흐름을 확인하는 것이다.

현재 근거로는 응답 구조가 full 실행마다 100%였고, EVAL-143 안전 경계도 수정 뒤 3회 반복
통과했다. 주요 영역 경계와 반복 동점도 표적 검사에서 안정됐다. 신규 카드 20장도 각각 실제
경로에서 도달했다. 말씀 추천 기능을 지인 베타에서 실제 문장으로 관찰할 준비는 갖춘 것으로 본다.

다만 최종 수정 이후 full 153건을 다시 실행하지 않았으므로, 현재 코드의 정확한 전체
primary·preferred·acceptable 비율은 아직 없다. 그 수치가 출시 문서에 꼭 필요하면 153회
검사를 한 번 더 실행해야 한다. 지인 베타를 시작하는 데 반드시 필요한 검사는 아니며,
이미 여러 차례 full 실행과 표적 반복 검사에 많은 토큰을 사용했다.

다음 단계는 단일 Luna 출력의 작은 변동을 계속 따라가며 태그를 늘리는 작업보다 지인 베타가
적절하다. 베타에서는 사용자가 입력한 원문이나 신원을 수집하지 않고, 본인이 자발적으로 제공한
익명화된 재현 문장과 선택 결과만 받아 검토한다. 안전 경로, 영역 선택 화면, 추천 말씀의
자연스러움, 뒤로가기와 삭제 흐름을 함께 확인하고, 같은 실패 유형이 반복될 때만 카드나
Analyzer 경계를 다시 조정한다.
